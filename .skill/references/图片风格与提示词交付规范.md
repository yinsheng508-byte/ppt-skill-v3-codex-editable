# 图片风格与提示词交付规范

本文只规定阶段1/2的风格来源、项目 `图片风格.md` 写法、它和 `PPT一致性.md` 的关系，以及向提示词和证据链的交接边界。

## 职责边界

阶段2生图链路按下面顺序理解：

| 环节 | 责任文档 | 说明 |
| --- | --- | --- |
| 版式秩序 | `PPT一致性.md` | 标题、模块页、页码、logo、公共元素和例外 |
| 画面气质 | `图片风格.md` | 配色、质感、媒介、主视觉语言、逐页图片规划和禁用项 |
| 派生计划 | `image_prompt_plan` | 从两份阶段1文档、deck/layout组件和批准正文整理出的每页执行计划 |
| 最终提示词 | `提示词建设规范.md` | 规定 `image_prompt_plan` 和 final prompt 怎么编译 |
| 生图证据 | `生图证据链.md` | 规定 route、packet、batch、evidence、result、hash、尺寸和历史请求 |
| 封面方向 | `封面风格候选规范.md` | 规定阶段2A四封面、用户选择、deck_style/layout_intent 和封面转正 |
| 用户记录 | `图片生成提示词.md` | 只展示生成成功且有图片结果的真实提交提示词 |

`image_prompt_plan` 是派生结果，不是第三份风格权威。上游规则改变时，先更新项目 `PPT一致性.md` 或 `图片风格.md`，再重新整理受影响页计划和请求；不要手改 final prompt 或 result 来制造一致。

## 输入与单一风格文档

阶段0只登记风格素材、参考图、用户原话、来源和用途，不创建 `图片风格.md` 空模板。用户可在阶段0、阶段1或阶段2提供风格描述、参考图或反例图；主控必须实际查看参考图，区分用户明确要求和主控解读，记录借鉴的配色、质感、构图、字体气质或禁用项，不把参考图里的无关文字和事实加入 PPT。

进入阶段1后，项目只保留两份用户可见视觉控制文档：

```text
阶段1_规划确认/PPT一致性.md
阶段1_规划确认/图片风格.md
```

`PPT一致性.md` 管版式秩序，写法见 [PPT一致性文档规范.md](PPT一致性文档规范.md)；`图片风格.md` 管画面气质，使用 `assets/templates/阶段1图片风格模板.md`。用户没有提供风格时，主控要给出具体方案，不能以“用户未提供”占位通过。

旧 `风格与提示词方案.md` 只作为历史恢复输入。显式迁移时，用 `pptctl.py migrate-image-style --run-dir <项目> --merged-file <主控合并文档>` 合并原文和新结构；新旧都有内容时必须先形成合并稿，不能覆盖用户原文。

## `图片风格.md` 写法

项目 `图片风格.md` 至少包含：

- `## 当前生效风格`：写清整体画面气质、配色角色、媒介、质感、光影、插画/摄影倾向、字体气质和信息密度。
- `## 禁用项`：写清不要出现的风格、元素、构图、文字效果、错误媒介和事实风险。
- `## 不同页面的应用`：按封面、内容页、章节页、流程页、图表页等页面角色说明如何应用同一风格。
- `## 逐页图片规划`：每页写主视觉、构图方向、重点元素和必要避让。
- `## 调整记录`：只记录历史变化，不参与新提示词编译。

规则必须具体、可执行、可检查。不要写“简洁高级、风格统一、好看”这类空泛形容词后直接通过。当前有效风格、必要禁用项和硬规则不能按首句、首行或固定字数截断；色号、数量、方向、小数和否定含义必须完整保留。

参考图沿用 `add-material --role-hint image_style` 登记。主控看图后，在 `design_contract.json.image_style_references` 记录 `material_id`、`interpretation`、`use`，必要时用 `slide_indices` 限定适用页；如果只是看图提炼风格，`mode=text_analysis` 要如实说明，不能编造 API 传图字段。

## 和 `PPT一致性.md` 的关系

两份文档共同进入每页计划，但职责不能混：

- 标题位置、模块页骨架、页码、logo、页眉页脚、公共视觉家具和例外边界，以 `PPT一致性.md` 为准。
- 配色、材质、光影、媒介、主视觉语言、风格禁用项和逐页画面方向，以 `图片风格.md` 为准。
- 同一条规则如果在两份文档里同义重复，主控在 `image_prompt_plan` 中合并一次。
- 两份文档冲突时，先回到阶段1确认文档修正，不在最终 prompt 末尾追加第二套相反规则。
- 任何 reference 规范原文都不直接塞进 prompt；final prompt 只吸收当前项目文档中适用于本页的实际规则。

正文只从批准的 `content.final_visible_text` 读取，角色通过条目索引引用。页面规划索引、资料页码、内部标题、来源说明、执行状态、路径、hash 和 QA 步骤都不能作为新增画面文字。

## 封面选择后的风格沉淀

用户选择封面后，选中的封面 style card 要被抽象成整套 PPT 的项目内视觉语言，而不是只保存为一张好看的封面。内部执行资产写入：

```text
_state/阶段2/deck_style.json
_state/阶段2/layout_intent.json
```

`deck_style.json` 沉淀 `visual_world`、`style_atoms`、`palette/color_contract`、`typography`、`image_language`、`motif_system`、`content_policy` 和 `forbidden_visuals` 等风格层规则；标题区、模块页、页码、logo 等版式秩序仍要能回到 `PPT一致性.md` 找到依据。

`design_contract.json` 写阶段1审美意图和封面候选策略，`deck_style.json` 写选定封面后真正锁定的视觉系统。`deck_style.json` 可以比 design contract 更具体，但不能违反已确认内容边界，也不能反向修改阶段1页面文字。

## 试样、返工与交付边界

试样默认总共5张，包含已选封面，通常新生成4张内页；复杂页可在4张内页名额内替换并记录理由，不自动追加到6张。试样图和正式图都放 `阶段2_图片版PPT/img/`，图片存在于 `img/` 不代表已确认；试样 selection、正式 result 和图片版 PDF manifest 才是当前状态依据。

中途改风格时，主控明确受影响页、可复用页和理由，只撤销受影响图片确认，不修改已确认正文。试样暴露整体风格问题时，先更新 `图片风格.md` 的当前规则并同步 deck/layout 字段，再重新整理受影响页 `image_prompt_plan`；不要直接手改最终 prompt 或保留冲突旧规则。

`阶段2_图片版PPT/图片生成提示词.md` 是下游成功记录文档：只展示生成成功且有图片结果的真实提交提示词和对应图片；参考图及借鉴范围等来源说明放在代码块外。生成中、生成失败、待重试请求、内部 ID、hash、执行日志、packet 和 evidence 留在 `_state/`。已在途请求按原快照回收，已有成功记录中的尺寸、来源说明和实际提示词如实保留，不因新表达规范改写历史，也不做全局关键词删除。提示词文档修复使用 `pptctl.py refresh-image-prompts --run-dir <项目>`，单独交付时用 `--output-dir` 连同依赖图片一起复制。

准备新画面计划时，先用 `image-prompt-sources` 只读查看来源，再按 [提示词建设规范.md](提示词建设规范.md#查看来源与登记计划) 用 `record-image-prompt-plan` 登记计划。内置生图工具调用前使用 `prepare-image-request` 获取不可变请求快照；API 批次自动完成同类准备。两条路线都不能在结果返回后重新编写提示词。
