# 提示词建设规范

本文只规定 `image_prompt_plan` 如何登记，以及 final prompt 如何从当前项目 `PPT一致性.md`、`图片风格.md`、批准正文和 deck/layout 组件编译出来。风格来源见 [图片风格与提示词交付规范.md](图片风格与提示词交付规范.md)，执行证据见 [生图证据链.md](生图证据链.md)，封面候选见 [封面风格候选规范.md](封面风格候选规范.md)。

## 目标

阶段2图片生成前，主控先整理本页当前有效的画面规则，再编译 final prompt。每次中转站生图都是独立任务，提示词必须脱离上一页或历史对话独立执行。精简发生在提交前，成功后按实际提交内容逐字交付。

主控负责从项目规则中选择、归并和表达本页真正需要的内容；runtime 只验证计划、来源摘要和请求快照，不把上游自然语言规则重新追加进 prompt。没有统一字数、规则数量或“所有来源逐条覆盖”的门槛。

阶段2 prompt 的内容来源必须是：

```text
页面规划.md 权威逐页规划表
-> 每页干净逐字稿.md 人类审阅稿
-> content.json
-> slide_prompt_briefs.json
-> design_contract.json
-> PPT一致性.md
-> 图片风格.md
-> deck_style.json
-> layout_intent.json
-> final prompt
```

已校验与逐页brief一致的 `content.final_visible_text` 是唯一页面文字源。图片模型不能自由新增页面文字；已确认页码策略是唯一明确声明的自动文字例外。
`每页干净逐字稿.md` 只用于用户审阅和一致性校对，不允许成为绕过 `页面规划.md` / `content.json` 的新增文字来源。

## 两层提示词

第一层：`slide_prompt_briefs.json`

放在：

```text
_state/阶段1/slide_prompt_briefs.json
```

它记录每页要表达什么，不直接等同于正式生图 final prompt。每个待生成内页在对应brief中保存 `image_prompt_plan`；封面候选计划先保存到 `design_contract.stage2_cover_option_strategy.option_briefs` 的对应候选，派发时带入style card。不新建第二份用户风格文档或独立台账。

第二层：final prompt

放在：

```text
_state/阶段2/final_prompts/
```

它是交给当前选定正式生图路线的最终提示词；默认给 `openai_image_api` 中转路线，用户明确指定或主控写明切换原因时才给 Codex 内置 `image_gen`。

## slide_prompt_briefs.json 建议字段

每页建议包含：

- `slide_index`
- `page_role`
- `message_goal`
- `final_visible_text`
- `visual_composition`
- `layout_family`
- `density_budget`
- `visual_anchor`
- `content_fidelity_policy`
- `main_visual_elements`
- `style_constraints`
- `negative_constraints`
- `acceptance_criteria`
- `image_prompt_plan`

这些字段供主控规划；不把字段名、路线、受众、验收步骤逐项展开给图片模型。有效的限制须完整进入画面计划。

## image_prompt_plan

```json
{
  "version": "1",
  "basis_hash": "sha256:当前适用源规则的摘要",
  "visual": ["本页具体构图、主视觉和信息关系"],
  "style": ["本页独立完整的图片风格继承与图像表现"],
  "layout": ["本页适用的PPT版式一致性、文字层级和位置关系"],
  "constraints": ["本页高风险错误的必要限制"],
  "text_roles": {"title": 0}
}
```

上例是字段说明；主控须填成具体画面要求并取得真实来源摘要，不能原样作为完成的计划。

- 计划是当前源规则的派生结果，不是另一套风格权威。主控核对项目 PPT 一致性、共同风格、页型规则、本页构图和必要禁用项，解决语义冲突与同义重复。主控把“PPT一致性 + 本页构图”整理进 `layout` 与 `visual`，把“图片风格继承 + 本页图像表现”整理进 `style`；不逐条照抄来源，也不让过期默认规则回流。
- 四个画面字段均为中文字符串列表。可选项为空时省略，`constraints` 和 `negative_constraints` 可为空，不以清晰度套话凑数。
- `text_roles` 使用批准正文条目的零基索引，不复制文字。支持 `title`、`subtitle`、`module_index`、`module_title`、`module_subtitle`、`page_number`；没有的角色可以省略，不猜测第一条一定是标题，不自动补章节编号。P0 阶段不支持 `section_label`、`chapter_label`、`eyebrow` 等普通页章节标签角色；普通内容页默认只使用 `title` 表达页面标题，不从跨页映射表或 `header_policy` 自然语言示例生成章节标签。正文区仅输出批准原文，条目之间以空行分段，不夹入“标题：”“章节编号：”等用途标签。角色映射放在正文区外的 `【页面设计】` 中，按条目顺序引用段落，例如“第1段作为章节编号，第2段作为章节标题；这些用途名称不出现在画面中”，不复制正文。共享模板中使用的角色必须绑定，`{slide_title}` 作为 `{title}` 的兼容写法；其他未绑定变量须先处理。
- 文字角色和页码策略在编译时确定性表达；标题、章节模板和安全区只作为主控整理计划的来源，最终编译器不再追加原始规则，而是输出主控已经整理好的要求。布局按文字角色描述位置，不另写一份标题文字。
- 页码由编译器依据已确认的 `page_number_policy` 单独生成一次；四个画面列表不另写页码开关、文字或样式。`text_roles.page_number` 可引用批准正文已有的页码，此时只安排位置与样式，不再生成数字。角色和policy冲突须先修正。
- 页码与共享组件的适用范围用页面角色列表 `applies_to` 和正整数列表 `exclude_slide_indices` 表达，关闭或豁免时不输出组件内容。封面默认不显示页码；用户明确启用且applies_to包含cover时，候选和正式封面一致执行。完整策略见 [PPT一致性文档规范.md](PPT一致性文档规范.md#页码策略)。
- `basis_hash` 只取当前适用源规则，排除计划自身、来源说明和时间戳。生成依据另外覆盖有效计划内容；写入计划不能造成循环hash。
- 主控负责语义完整性；runtime 校验类型、引用、来源是否过期、内部信息泄漏和请求快照，不靠正则或相似度猜测意思，也不把某条来源原文是否出现当作规则完整的证明。

## 查看来源与登记计划

先只读查看当前来源、来源摘要和已有计划：

```bash
python3 .skill/scripts/pptctl.py image-prompt-sources --run-dir "<项目绝对路径>" --slide-index 2
python3 .skill/scripts/pptctl.py image-prompt-sources --run-dir "<项目绝对路径>" --slide-index 1 --option-id A
```

返回的 `sources` 包含批准文字、项目 PPT 一致性、适用风格、页面组件、安全区和页码策略；`basis_hash` 是当前源摘要，`plan` 是已保存计划。主控据此核对规则，将整理后的草稿JSON保存在项目 `_state/` 的临时准备文件中。草稿包含 `visual`、`style`、`layout`、`constraints` 和 `text_roles`；其中visual/style不能为空，layout/constraints可以为空，正文不写进草稿。

再登记内页或候选计划：

```bash
python3 .skill/scripts/pptctl.py record-image-prompt-plan --run-dir "<项目绝对路径>" --slide-index 2 --plan-file "<项目绝对路径>/_state/阶段2/本页画面计划草稿.json"
python3 .skill/scripts/pptctl.py record-image-prompt-plan --run-dir "<项目绝对路径>" --slide-index 1 --option-id A --plan-file "<项目绝对路径>/_state/阶段2/封面A画面计划草稿.json"
```

`--slide-index` 使用真实页序，示例中的1须替换为实际封面页；`--option-id` 只接受A/B/C/D。`--plan-file`相对路径按命令当前工作目录解析，建议使用绝对路径。登记只允许阶段1或阶段2，不发起生图，也不代替阶段确认。

命令填写版本和当前来源摘要后保存主控已经整理好的计划，不自动补入一致性规则、共享组件、安全区或风格禁用项。主控仍须核对完整风格、页级/候选限制与语义冲突；它不会自动读懂并改写自然语言。重新准备时根据当前来源重新整理草稿，不把含旧组件的完整plan原样登记。普通页章节标签不是默认组件；未显式 opt-in 的跨页章节映射、眉题示例和未绑定 `chapter_tag` 安全区不能进入 plan。页码规则只保存在现有policy中。

内页计划写回 `slide_prompt_briefs.json` 对应页；候选计划写回 `design_contract.json` 对应option brief，派发再同步style card，不通过手改已派发卡片绕过来源。源规则改变后先重新查看和登记计划，再重新派发packet；这些命令不改写历史请求或成功文档代码块。

## final prompt 表达顺序

每份新请求固定使用下面四段，便于人读、AI 主控复核和中转站独立执行：

1. `【画面文字】`：批准的完整原文，保留条目内换行与原有编号，条目间以空行分段；用途标签不进入正文区。
2. `【页面设计】`：文字角色、本页适用的 PPT 版式一致性、本页构图和一次页码策略。先说明“这一页像不像同一套PPT”，再说明“这一页具体怎么排”。
3. `【视觉风格】`：本页完整的图片风格继承和本页图像表现。先说明“图片像不像同一位画师”，再说明本页要画什么。
4. `【关键约束】`：本页高风险错误、文字边界和必要避让。只写会直接造成生成错误的内容，不重复页面设计或视觉风格。

四段之外不另设“构图”“文字与布局”“排版要求”“画面限制”或独立页码行。相同要求集中表达。页面目的、受众、密度预算、视觉锚点和验收标准只在能转成具体画面要求时采用，不强制输出这些标签。

正文区外的文字角色说明放在 `【页面设计】`，用第几段说明标题、章节编号等用途；它是布局指令，不是新增可见文字。禁止夹入的是系统添加的用途标签，批准正文原本包含的同名术语仍原样保留。历史成功请求曾使用角色标签时保留当时真实提示词，新请求采用纯正文与外部段落引用。

系统生成指令仅写“横版中文PPT”，不添加像素尺寸、数字画幅比例、分辨率或1K/2K/4K要求。尺寸通过接口参数设置，实际宽高、比例与清晰度通过结果验收；内置备用工具只传实际支持的参数，不把内部尺寸目标拼回prompt。

这项边界只作用于生成指令。批准正文中已有的“16:9”“1672×941”“4K显示器”、英文单位、公式或技术词必须原样呈现，不能对整个提示词执行尺寸或术语删除。

## 中文文字规则

正式图片以批准的中文内容为准，保留其中的英文专业术语和单位。缺少批准正文或brief与content不一致时，定位到具体页处理，不回退到内部索引标题。

文字边界集中表达一次，例如：

```text
画面文字以给定内容为准，保留数字、单位、年份和专业术语，不另加装饰文字。
文字完整清楚，图形与纹理避让文字。
```

这些文字要求集中表达一次，放在 `【关键约束】`，不再单独输出 `content.title`、内部页序或说明性编号。规则精简不处理正文，不删除重复数据值、换行或反引号。

风格和限制不能按首句、首行或固定字数截断；多句规则、小数、色号、数量、方向和否定含义完整保留。主控合并同义要求；runtime只对画面规则中规范化后完全相同的项去重，不以删除否定词“简化”禁用项。

来源说明、参考图处理方式、跨候选安排、阶段流程、状态、文件路径、内部ID、图层归属和QA步骤不进入画面指令。提交前检查针对指令区与源字段，不清洗正文；用户页面可以合法讲解“模型”“参考图”“hash”等内容。

## 统一 prompt 片段

阶段2全套图片生成前，主控从 `PPT一致性.md`、`deck_style.json.header_policy` 和 `layout_intent.global_layout.header` 等当前有效来源中整理普通内页页面标题规则。除封面、目录、章节和结束页等明确豁免页面外，主控在每页 `layout` 中写入同一具体位置、字体和装饰要求。普通内容页不默认提取章节标签、眉题或模块导航条；这些组件必须另有明确 opt-in 与批准文字来源。下例仅演示空间描述，实际值须来自本项目规划：

```text
标题位于左上方，左边距为画布宽度的8%，顶部留白为画布高度的8%；使用深蓝加粗黑体，标题下方放细蓝线，正文从标题区下方开始。
```

如果PPT有多个模块介绍页或章节页，主控为所有 `section_divider` 页确定同一具体结构。章节编号、标题和短说明通过 `text_roles` 引用批准正文，不根据内部页序新增文字。空间描述示例：

```text
章节标题位于画面左侧中部，短说明紧接标题下方，右侧放半透明主视觉；已批准的章节编号置于标题上方的小圆角容器。
```

组件由主控在准备 `image_prompt_plan.layout` 时按页整理一次，最终编译不再追加共享片段。每次请求必须独立完整，不用“沿用上一页”“使用同一字号”代替具体要求。来源组件保留内部用于追溯和过期判断。

## 封面候选 prompt

四张封面候选的final prompt基于当前图片风格和对应style card中的画面计划，共同配色、媒介、字体和禁用项保持一致。

差异可以来自：

- 构图。
- 主视觉。
- 视觉重点。
- 主视觉与标题的大小关系。
- 信息密度。

差异须体现在构图和视觉重点，不只替换同义词。每份请求只写自己的构图，不写“四张需要不同”等整批安排；通用封面规划中冲突的位置要求须先解决，不能后置追加。

## 全套图片 prompt

全套图片生成时，主控大模型根据 PPT 类型判断内页复杂度：

- 专业型内容可以更丰富。
- 演讲型内容应更简洁。
- 方案型内容要兼顾信息密度和高级感。
- 资料改造型内容优先保留事实和原逻辑。
- 护理宣教型内容要专业可信、温和、可执行。
- 学术答辩型内容要保留论证链和证据锚点。
- 创赛路演型内容要有说服力但不能夸大事实。
- 仿做升级型内容基本不变，只升级页面设计和表达清晰度。
- 默认不加可见页码；不要把阶段1规划索引或原材料页码画进页面。
- 普通内页的计划须包含统一且具体的左上页面标题要求，避免标题区漂移；未显式启用时不带章节标签。
- 多个模块介绍页的计划须包含同一具体版式骨架，组件只解析一次。

## 阶段2B试样 prompt

阶段2B先生成试样时，trial prompt 仍是正式质量的 prompt：

- 必须使用当前选定正式生图路线，默认 `openai_image_api`。
- 尺寸继续由独立接口参数设置，试样与正式图执行相同的实际图片验收；不在prompt中追加尺寸指令。
- 必须保留完整证据链。
- 必须包含每页 `final_visible_text`。
- 必须使用已归并当前 PPT 一致性、当前图片风格和适用deck/layout组件的有效画面计划。
- 如果试样失败，默认修改阶段2设计规划或 prompt，不修改阶段1内容资产。

生成式返工先更新受影响页视觉计划，再重新派发完整目标画面；不不断追加“其余不变”。真正使用编辑接口并提交输入图时，才可引用该图说明保留和修改区域。

## 请求与成功历史

新请求须使用当前有效计划和提示词规范版本；计划来源包含项目 `PPT一致性.md` 和 `图片风格.md` 中本页适用规则。冻结前重新编译应提交内容，与packet.prompt、prompt_hash及batch摘要核对；不一致就重新派发，不能仅补版本号或手改prompt/hash通过。

旧待发任务和失败后的新重试先补齐当前计划并重新派发。已在途请求按原冻结快照回收；旧成功图片和实际prompt保持原样，不能因表达版本升级自动重生或改写历史。

异步返回时，即使当前sources暂时不完整，或正文与brief正处于不同步状态，已成功返回的图片仍按原冻结提示词登记历史，不替代当前页面结果；先修复当前规划，再由主控核对是否可复用。当前资料暂不可编译不能成为丢弃成功请求证据或用新prompt覆盖旧记录的理由。

`图片生成提示词.md` 只展示有成功图片结果的请求，代码块逐字保留实际提交prompt。参考图及借鉴范围在代码块外说明，内部ID、hash和执行日志留内部。转正、复用和文档修复不伪造新调用，生成失败只留内部排查。

runtime负责确定性校验、编译、请求记录和证据，不负责审美判断。
