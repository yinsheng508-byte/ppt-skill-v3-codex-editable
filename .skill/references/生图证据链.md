# 生图证据链

本文只规定阶段2正式生图路线、packet、batch、evidence、result、hash、尺寸、比例、并发和历史请求处理。上游风格来源见 [图片风格与提示词交付规范.md](图片风格与提示词交付规范.md)，final prompt 编译见 [提示词建设规范.md](提示词建设规范.md)，封面候选选择见 [封面风格候选规范.md](封面风格候选规范.md)。

证据链证明图片从哪里来、用什么提示词生成、是否有真实结果和尺寸事实；它不负责审美判断，也不替代用户确认。

## 正式路线

阶段2封面风格候选、阶段2B试样和阶段2全套整页图片有两条正式生图路线：

1. `openai_image_api`：OpenAI-compatible 中转 API 路线。默认走国内直连中转站，适合阶段2批量稳定执行。
2. `codex_image_gen`：Codex 内置 `image_gen` 官方路线。作为显式备用路线保留。

路线是阶段2内部执行策略，不新增用户确认点。无论走哪条路线，都必须先生成 packet 和 batch manifest，再按 packet 生成图片并记录正式 result；不能直接把一张图片放进阶段目录当作已完成。

## 默认选择和切换

默认规则：

- 新项目阶段2A、阶段2B和阶段2正式整页图片默认使用 `openai_image_api`。
- 用户说“走中转 API / 用 API / 用苍原 / 国内直连 / 用 `openai_image_api` / 默认路线”时，使用 `openai_image_api`。
- 用户说“官方路线 / image gen / 内置 image_gen / 用 Codex 生图 / 用 `codex_image_gen`”时，使用 `codex_image_gen`。
- 如果 `openai_image_api` 缺少密钥、调用失败、没有真实 API evidence 或返回图不可用，可以切回 `codex_image_gen`，但必须写入主控说明或 decision basis，且不能把失败 API packet 的 result 手工补成成功。
- 如果 `codex_image_gen` 工具不可用、生成失败、输出无法保存到项目，或连续出现严重文字/构图问题，主控可以切回 `openai_image_api`，但必须写入主控说明或 decision basis。

同一个阶段2确认图集合应尽量使用同一条路线。若同一批里混用两条路线，必须在 batch/result 中逐页写清 `image_generation_route`，并由主控在阶段决策或对用户说明中解释原因。

## 尺寸和清晰度策略

阶段2正式图片默认目标尺寸：

```text
1672x941
```

这是 16:9 的 1K 级默认目标。生成器实际返回可能存在轻微尺寸差异；轻微差异本身不是质量风险，但必须如实记录实际宽高、目标尺寸、容差和是否落在目标容差内。`1600x900` 是当前优先底线，低于该底线时作为清晰度风险记录，由主控按实际效果决定继续、重试或切路线。

统一规则：

- 尺寸通过接口参数设置，实际宽高、比例和清晰度分别核验。新prompt只描述横版画面，不自动加入像素尺寸、数字画幅比例或1K/2K/4K指令；批准正文中的尺寸知识原样保留。
- packet 必须写入 `target_size=1672x941`、`preferred_minimum_size={width_px:1600,height_px:900}`、`target_size_tolerance_px` 和 `size_policy=preserve_generated_raster_no_downscale`。
- result 必须记录实际 `width_px`、`height_px`、`target_size`、`preferred_minimum_size`、`target_size_tolerance_px`、`meets_target_size`、`meets_preferred_size` 和 `size_warnings`。
- 默认 canonical 策略是保留生成器返回的原始 raster；不要为了文件体积、兼容性或旧模板主动把图片压缩、降采样或另存为更小尺寸。
- `normalize_at_stage2` 如果会缩小源图，不再作为硬错误处理，但必须记录 `postprocess_downscaled...` warning，主控据此判断是否继续。
- 如果任一路线返回低于 `1600x900`，不要本地拉伸冒充 1K 级结果；应保留真实返回尺寸并记录 `meets_preferred_size=false` 和 `size_warnings`，主控可按实际清晰度决定继续、重试提示词或切换路线。
- 如果所有可用路线都无法稳定返回 1K 级结果，可以继续推进，但阶段决策或对用户说明里应提醒这是低于优先底线的结果。

比例与像素宽高分别验收。目标比例为 `16:9`，按实际图片宽高计算相对误差 `abs((width/height)/(16/9)-1)`；默认相对比例容差为 **2%（0.02，包含边界）**。它与宽、高各自的像素容差无关，不能因为达到最低宽高就判定比例通过。

新结果同时记录 `target_aspect_ratio`、`aspect_ratio_error`、`aspect_ratio_tolerance` 和 `meets_target_aspect_ratio`。偏差超过2%时保留原图，记录比例warning，由主控核对后决定返工或有依据地接纳；不得自动拉伸或裁切。旧结果没有这些字段时可读取实际图片只读核算，不伪造原记录，也不自动撤销已有确认。以上比例和尺寸数据留内部验收，不追加到prompt。

## Codex Image Gen 显式备用路线

官方路线使用内置 `image_gen` 工具，由主控大模型逐个 packet 调用。runtime 只负责派发 packet、记录 batch/result 和校验证据；本地 CLI 不会自动调用对话工具。此路线不是新项目默认路线，只有用户明确要求、API 路线不可用或主控写明切换原因时使用。

派发 packet：

```bash
python3 .skill/scripts/pptctl.py dispatch-cover-options --run-dir <项目目录> --route codex_image_gen
python3 .skill/scripts/pptctl.py dispatch-stage2-trial-first5 --run-dir <项目目录> --route codex_image_gen
python3 .skill/scripts/pptctl.py dispatch-stage2-remaining --run-dir <项目目录> --route codex_image_gen
```

主控执行：

1. 使用 `prepare-image-request` 校验新请求并取得不可变快照，读取返回的完整 `prompt` 和真实图片输入。
2. 阶段2使用 `image_gen`，仅传工具实际支持的字段；不把内部 `image_gen_input` 对象直接当成工具参数。
3. 原样提交冻结prompt，不追加尺寸或流程说明。`image_gen_input.size` 是内部执行目标，不代表工具支持该参数或输出已达成；实际结果另行验收。
4. 将最终选定输出复制到 packet 的 `expected_output_relpath` 或临时项目路径，默认不主动降采样或压缩。
5. 运行 `record-image-result`，用不可变快照路径作为packet，传入 `provider=codex_image_gen`、`source=codex_image_gen`、`generation_id`、`tool_call_id` 和 `image_gen_result_id`。如果未提供 `--image-gen-evidence-path`，runtime 会在 `_state/.../image_gen_calls/` 自动写 controller-recorded evidence，并读取实际图片尺寸入账。

记录示例：

```bash
python3 .skill/scripts/pptctl.py record-image-result \
  --run-dir <项目目录> \
  --packet <packet.json> \
  --image <image_gen输出图> \
  --provider codex_image_gen \
  --source codex_image_gen \
  --generation-id <generation-id> \
  --tool-call-id <tool-call-id> \
  --image-gen-result-id <image-gen-result-id>
```

## OpenAI Image API 中转路线

中转 API 路线使用 OpenAI-compatible batch runner，是阶段2新项目默认生图路线。

默认配置：

- 中转站入口：`https://k.grsai.com/`
- 实际 API `base_url`：`https://eb.grsaiapi.com/`
- 生成端点：`/v1/images/generations`
- API key：优先从环境变量 `PPT_IMAGE_API_KEY` 读取；没有环境变量时读取本机密钥文件 `~/.codex/secrets/ppt-skill-v3/image_api_key`，也可通过 `PPT_IMAGE_API_KEY_FILE` 指定其他本机密钥文件。密钥不能写入 Skill 文档、项目产物、batch 或日志。
- 模型：`gpt-image-2.5`
- 默认尺寸：`1672x941`
- 默认质量：`high`
- 默认输出格式：`png`
- 默认响应格式：`b64_json`
- 单次生图任务超时：`500s`，覆盖 API 请求、响应解析和返回图片 URL 下载。
- 单个 batch/run 同组最大并发：`6`；多个独立 batch 可以由主控同时运行，不设全局互斥。
- 新默认路线要求请求体显式发送 `response_format=b64_json`，runner 直接保存返回的 base64 图片；只有兼容网关返回公网图片 URL 时，才写入 evidence/result 的 `provider_image_url`。

首次使用可先配置一次本机密钥文件：

```bash
python3 .skill/scripts/pptctl.py configure-image-api-key --stdin
python3 .skill/scripts/pptctl.py image-api-key-status
```

派发和执行：

```bash
python3 .skill/scripts/pptctl.py dispatch-cover-options --run-dir <项目目录> --route openai_image_api
python3 .skill/scripts/pptctl.py dispatch-stage2-trial-first5 --run-dir <项目目录> --route openai_image_api
python3 .skill/scripts/pptctl.py dispatch-stage2-remaining --run-dir <项目目录> --route openai_image_api

python3 .skill/scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage cover-options
python3 .skill/scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage stage2-trial-first5
python3 .skill/scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage stage2-remaining
```

`--stage stage2` 只用于主控明确决定跳过试样时运行全套正式整页图片；新流程主路径是 `stage2-trial-first5` 通过后再运行 `stage2-remaining`。

## Batch 与并发

所有正式生图都必须有 batch manifest：

- 封面候选：`_state/阶段2/cover_options/batches/<execution_group_id>.json`
- 阶段2B试样：`_state/阶段2/trial_first5/batches/<execution_group_id>.json`
- 阶段2正式图片：
  - `codex_image_gen`：`_state/阶段2/image_gen_batches/<execution_group_id>.json`
  - `openai_image_api`：`_state/阶段2/image_api_batches/<execution_group_id>.json`

每个新 batch 只有这一份可变、权威 manifest，记录成员、当前进度、状态和关联 ID；不再为每次更新写完整 `history/` snapshot。历史由冻结请求、路线 evidence、正式结果和决策/事件重建；旧项目的 history snapshot 继续可读，不自动迁移或删除。
中转 API 路线必须并发生成：

- 阶段2A 四张封面候选必须作为同一个 `execution_group` 并发运行图片 API 批量执行器。
- 阶段2B 试样必须作为独立 `execution_group` 并发运行图片 API 批量执行器；默认总共5页确认范围，包含已选封面，通常新增4张内页；已由选中封面候选转正的页面直接复用，不再进入试样 batch。
- 阶段2B 试样通过后的剩余图片页必须按 packet 的 `execution_group` 并发运行图片 API 批量执行器。
官方 `image_gen` 路线同样必须按 packet 和 batch 入账；受对话工具能力限制，主控可以逐个调用工具，但不能跳过 batch manifest、packet、evidence 或逐张 result 记录。

## 证据归属与图片去重

- 冻结请求是实际提交的提示词、参数、输入引用和请求身份的唯一事实来源。
- 路线 evidence 保存提供方返回、调用 ID、状态和必要原始信息；正式 result 保存最终采用页面、图片 SHA、尺寸、质量结论及两者关联。
- 成图以 SHA 在 `_state/阶段2/prompt_history/result_images/` 保留一份不可变内部证据；页面采用入口优先硬链接，无法链接时才单次复制。提示词历史和轻量 attempt 只能保存路径、SHA 和关联 ID，不能再另存同一图片或完整 result 镜像。
- 新项目不写 `result_receipts`；旧 receipt、旧完整 ledger 和 batch history 只读兼容。

## 图片用途

正式图片用途分三类：

- `cover_option`：阶段2A四张封面候选；用户选中且质量通过的候选可直接转正为封面页 `full_slide`。
- `trial_first5`：阶段2B试样图，供用户确认视觉、文字、密度和风格方向；内部名称沿用历史标识；默认总共5页，包含已选封面，短项目按实际页数。
- `full_slide`：阶段2B正式整页页面图，后续打包为图片版 PDF。
- `stage2_text_removed_background` / `stage3_background`：旧阶段3无字背景相关 purpose，只作为 legacy 识别，不作为新的正式 production 路线。

封面候选不能整组进入阶段2正式页面图，未选中的候选永远不能进入图片版 PDF。用户选中且主控检查通过的封面候选应直接 promotion 为正式 `full_slide` 封面结果，避免阶段2B重复生图。试样必须经用户确认和 runtime promotion 后，才能进入正式 `full_slide` results；已由封面候选转正的页面不再进入试样生图 packet。用户确认通过的试样页默认复用为正式页面，不为生成全套图片而重生。图片版 PDF 只使用 `full_slide`。

## Canonical 图片策略

请求尺寸不等于最终返回文件一定是该像素尺寸。阶段2必须使用同一套 canonical 策略：

- `preserve_api_raster`：阶段2确认图保留实际生成返回尺寸。字段名沿用历史命名，也适用于 `codex_image_gen`。
- `normalize_at_stage2`：阶段2入账时就生成 canonical 可见图，阶段2 PDF 使用 canonical 图。

若发生归一化，必须记录 `original_api_output`、`postprocess.manifest_path`、原图 sha、canonical 图 sha、尺寸和方法；证据仍指向真实原始输出，正式 `image_result.image_path` 指向用户可见 canonical 输出。归一化如果把生成原图降采样到更小尺寸，应写入 `size_warnings`，由主控判断是否接受。

## 提示词要求

- 依照 [提示词建设规范.md](提示词建设规范.md) 编译有效的 `image_prompt_plan`，正文仅来自批准的 `content.final_visible_text`，保留专业术语、数字、单位和换行。
- 不新增英文占位、乱码或伪文字；不额外加入内部标题、页序或说明性编号。页码只依据已确认policy生成一次。
- 每页提示词包含本页构图、主视觉、完整当前风格、具体文字布局和必要禁用项；页面目的、资料来源、执行说明和内部字段留在规划或台账。
- 封面候选保持共同配色、媒介、字体和限制，以构图和视觉重点区分；单张请求只包含自身要求。
- 试样和正式图片使用相同的当前风格及适用deck/layout组件，主控先归并到计划，编译后不再追加原始组件。
- 新请求冻结前核对计划、实际prompt及摘要。旧待发包重新准备，已在途及成功历史快照不改写；成功文档逐字保留实际prompt，参考来源说明在代码块外。

用户可读 `阶段2_图片版PPT/图片生成提示词.md` 不在每张图片返回时重建。四张封面完成、五页试样完成、剩余页完成以及显式刷新/导出时必须完整刷新；任何交用户确认的节点都必须使用最新文档。

真实编辑接口及内置备用路线使用的本地输入图，在准备请求时冻结到 `_state/阶段2/prompt_history/input_images/`，记录原始路径、归档路径和内容hash。API提交及内置工具调用使用归档路径，原输入随后变化不影响在途请求；归档文件本身被改动时不能继续提交。作为风格来源的参考图存档不等于实际传入了图片。

历史兼容draw路线若使用远端URL，只冻结URL字符串，不承诺远端图片字节已固定，也不把它描述为本地输入图快照。并发准备使用专用锁，每次实际请求获得独立ID；这些执行信息只留内部证据，不加入模型提示词。

## 禁止冒充

以下不能冒充正式图片：

- 本地擦字。
- inpaint 或本地修补。
- HTML/canvas/SVG 渲染。
- 浏览器截图。
- source replay。
- fixture。
- copied source render。
- 复制旧图冒充新图。
- 只有图片文件，没有 packet、batch、对应路线 evidence 和 result 记录。

## 主控检查

主控大模型在提交用户确认前检查：

- 图片是否真实来自选定正式路线：默认 `openai_image_api`，或显式 `codex_image_gen`。
- 每张 result 是否有 `image_generation_route`、对应结果 ID、对应 evidence path、`image_sha256` 和 batch 记录。
- 中转 API 路线同组多张图片是否按并发方式调用。
- 阶段2是否使用一致 canonical 图片策略；如有 postprocess，原始输出和 canonical 输出是否都可追溯。
- 试样是否先于剩余页面供用户确认。
- 已选封面候选是否在质量通过后直接转正，且未进入阶段2B重复生图。
- 试样 promotion 是否保留原 trial result、trial image 和 evidence。
- 中文文字是否可读。
- 页面主题是否明确。
- 风格是否统一。
- 阶段2正式图是否记录 `1672x941` 目标、`1600x900` 优先底线、容差、`meets_target_size`、`meets_preferred_size` 和必要 `size_warnings`；低于优先底线时是否清楚记录风险。
- 实际图片相对16:9的比例偏差是否在2%以内（包含边界），四个比例字段是否与真实宽高一致；比例通过不代替清晰度与文字验收。
- 是否存在任何后处理把生成图压缩、降采样或另存成更小尺寸；如存在，是否已作为质量风险记录。
- 信息层级是否清楚。
- 是否需要返工。
