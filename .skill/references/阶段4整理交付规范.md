# 阶段4整理交付规范

本文件定义阶段4文件整理交付能力。阶段4只整理当前项目中识别到且实际存在的对应产物，不生成新的 AI 图片、PPT、逐字稿或教案。它可以把已存在的阶段3逐字稿 PDF 和教案设计 PDF 确定性渲染为 `216 DPI / 3x_72dpi` PNG 交付副本。

## 进入与恢复

进入方式：

- 阶段3输出完成后，主控建议执行阶段4整理。
- 用户明确要求把当前最终产出物整理成一个主题文件夹时，由主控恢复项目事实后判断是否执行阶段4整理动作。

执行前先按 `恢复与防漂移协议.md` 恢复项目事实：

- 确认当前目录是具体项目目录，或先在 `PPT输出/` 下定位具体项目。
- 读取 `_state/project_state.json`、最近 `_state/decisions/` 和当前阶段目录。
- 状态、`user_artifacts`、`expected_user_paths`、标准路径和兼容旧路径都可以作为候选线索；候选文件实际存在就纳入。
- 当前项目仍在等待用户确认时，也可以整理已识别到的对应文件；但必须在回复中说明整理不代表用户已确认该阶段。

整理器本身不写阶段切换 decision，不修改 `project_state.current_stage`，也不改变确认状态。主控确认整理结果后，才可记录 `stage4_deliverables_organized` 决策并把项目标记为 completed。

## 输出位置

在当前项目 `阶段4_文件整理交付/` 下创建或刷新一个主题文件夹：

```text
PPT输出/<项目文件夹>/
  阶段4_文件整理交付/
    <主题名称>/
```

`<主题名称>` 按 `交付文件命名规范.md` 的 `<命名前缀>` 生成：默认取封面第一页主题；用户提供明确编号时，使用 `<用户编号> <封面第一页主题>`；取不到时用项目名兜底。主题名称可以和项目文件夹名称重复。

不要在项目根部单独创建 `<主题名称>/`，也不要新建 `最终交付/` 外层目录。

## 文件结构

整理后的基础目标结构为：

```text
阶段4_文件整理交付/
  <主题名称>/
    图片素材/
      slide_001.png
      slide_002.png
      ...
    逐字稿图片/              # 仅逐字稿 PDF 存在且渲染成功时创建
      page_001.png
      page_002.png
      ...
    每页干净逐字稿.md
    <主题名称>｜图片版PPT.pdf
    <主题名称>｜逐字稿.docx
    <主题名称>｜逐字稿.pdf
```

K12 项目且阶段3教案 DOCX/PDF 已存在时，额外纳入：

```text
阶段4_文件整理交付/
  <主题名称>/
    教案设计图片/            # 仅教案 PDF 存在且渲染成功时创建
      page_001.png
      page_002.png
      ...
    <主题名称>｜教案设计.docx
    <主题名称>｜教案设计.pdf
```

中间未识别到或实际不存在的文件直接跳过，不生成空文件、占位说明或交付清单。只有对应 PDF 存在且 `pdftoppm` 渲染成功时，才创建 `逐字稿图片/` 或 `教案设计图片/`；非 K12 项目不创建教案文件、教案占位或空的教案图片目录。

## 纳入规则

- `图片素材/`：复制 `阶段2_图片版PPT/img/slide_*.png` 中的正式页面图片；不复制封面候选、前5页试样、联系表、QA 预览或 `_state` 中的图片。
- `每页干净逐字稿.md`：复制 `阶段1_规划确认/每页干净逐字稿.md`，保持这个固定文件名。
- `<主题名称>｜图片版PPT.pdf`：复制已存在的阶段2图片版 PDF，兼容旧路径 `阶段2_图片版PPT/pdf/图片版PPT.pdf`，目标文件名统一使用当前主题名称。
- `<主题名称>｜逐字稿.docx` 与 `<主题名称>｜逐字稿.pdf`：复制阶段3逐字稿 Word/PDF。Markdown 版逐字稿是阶段3源稿，不放入整理文件夹。
- `逐字稿图片/page_*.png`：当 `<主题名称>｜逐字稿.pdf` 存在时，用 `pdftoppm -png -r 216 -forcenum` 从整理后的 PDF 副本导出逐页图片。`216 DPI` 是 PDF 基准 `72 DPI` 的 3 倍；不硬写固定像素，runtime 记录实际宽高、页数和 sha256。
- `<主题名称>｜教案设计.docx` 与 `<主题名称>｜教案设计.pdf`：识别到 K12 教案 Word/PDF 且文件存在时复制。Markdown 版教案和说明类文件不放入整理文件夹。
- `教案设计图片/page_*.png`：当 `<主题名称>｜教案设计.pdf` 存在时，用同一 `pdftoppm` 规则导出逐页图片。非 K12 项目或缺少教案 PDF 时直接跳过。

阶段4不复制历史编辑稿，也不把外部编辑稿放入 `阶段4_文件整理交付/<主题名称>/`。若用户另外要求保留外部稿，主控应单独说明它是额外文件，不属于阶段4标准整理结构。

## 覆盖与清理

- 阶段4整理动作默认复制文件到 `阶段4_文件整理交付/<主题名称>/`，并覆盖同名目标文件。
- 如果主题文件夹已存在，不默认删除用户手动加入的其他文件。
- 逐字稿和教案图片导出前只清理对应图片目录里的受控文件 `page_*.png`，不得删除用户手动加入的其他图片或说明文件。
- 对本次缺失的产物，不创建目标文件；如旧主题文件夹里已有同名旧副本，主控应提醒用户它可能是历史残留，只有用户明确要求清理时才删除。
- 如果 `pdftoppm` 不可用、PDF 损坏或渲染失败，阶段4整理不整体失败；已存在的 DOCX/PDF 和其他交付物继续复制，runtime 在 JSON 摘要的 `skipped` 中记录对应图片导出失败原因。

## Runtime 建议

优先使用被动命令：

```bash
python3 .skill/scripts/pptctl.py organize-deliverables --run-dir <项目目录>
```

该命令只能读取项目状态、复制符合规则的已存在文件，并把已存在的阶段3逐字稿/教案 PDF 渲染成整理目录中的 PNG 副本，然后输出 JSON 摘要；不能生成新的 AI 图片、PPT、逐字稿或教案，不能写 decision，不能把文件存在当作阶段完成依据。

跨平台环境：

- 默认只使用 `pdftoppm`，不使用备用渲染器。
- 可用 `PPT_SKILL_PDFTOPPM` 指向 `pdftoppm` 或 `pdftoppm.exe` 的完整路径。
- 可用 `PPT_SKILL_POPPLER_PATH` 指向 Poppler bin 目录；Windows 下 runtime 会查找 `pdftoppm.exe`，macOS/Linux 下查找 `pdftoppm`。
- 未设置环境变量时，runtime 会先查找 `PATH`，再尝试常见 macOS/Homebrew、Linux 和 Windows Poppler 安装路径。

## 完成记录

阶段4整理执行成功后，主控检查 JSON 摘要或 manifest：

- 复制了哪些文件。
- 渲染了哪些 PDF 图片。
- 哪些产物缺失或被跳过。
- `pdftoppm` 是否可用，失败原因是否只影响图片派生。
- `copied` 是否包含已确认阶段要求的核心交付物。
- 已确认阶段的核心产物是否被记录为 `source_missing`。

主控确认整理结果可交付后，记录 `stage4_deliverables_organized` 决策。该决策必须引用 `_state/阶段4/organize_summary.json` 或 `_state/阶段4/deliverable_manifest.json`，并由 runtime 校验 `schema_version`、`status`、`project_name`、`run_dir`、`topic`、`organized_dir`、`copied`、`rendered`、`skipped` 和 `created_at`。只提供整理目录、没有有效 summary/manifest，不能把项目标记为完成；整理器命令本身不是阶段完成依据。

已确认阶段的核心产物如果在 `skipped` 中记录为 `source_missing`，不能写完成决策，应回到对应阶段补齐或重新整理。`pdftoppm_missing`、`pdf_render_failed` 只影响 PDF 图片派生；只要对应 DOCX/PDF 核心文件已经复制，可以记录为 skipped 后继续完成。
