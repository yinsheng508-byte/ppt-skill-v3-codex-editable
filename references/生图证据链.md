# 生图证据链

## 正式路线

阶段2封面风格候选、阶段2B试样、阶段2全套整页图片和阶段3保真去字背景有两条正式生图路线：

1. `codex_image_gen`：Codex 内置 `image_gen` 官方路线。默认先走这条路线。
2. `openai_image_api`：OpenAI-compatible 中转 API 路线。用户明确指定、官方路线不可用、官方路线连续失败，或主控判断中转 API 更适合批量稳定执行时使用。

路线是阶段2/阶段3内部执行策略，不新增用户确认点。无论走哪条路线，都必须先生成 packet 和 batch manifest，再按 packet 生成图片并记录正式 result；不能直接把一张图片放进阶段目录当作已完成。

## 默认选择和切换

默认规则：

- 新项目阶段2A、阶段2B和阶段3背景都先使用 `codex_image_gen`。
- 用户说“走中转 API / 用 API / 用 grsai / 用 `openai_image_api`”时，使用 `openai_image_api`。
- 用户说“官方路线 / image gen / 内置 image_gen / 默认路线”时，使用 `codex_image_gen`。
- 如果 `codex_image_gen` 工具不可用、生成失败、输出无法保存到项目，或连续出现严重文字/构图问题，主控可以切换到 `openai_image_api`，但必须写入主控说明或 decision basis。
- 如果 `openai_image_api` 缺少密钥、调用失败、没有真实 API evidence 或返回图不可用，可以切回 `codex_image_gen`，但不能把失败 API packet 的 result 手工补成成功。

同一个阶段2确认图集合应尽量使用同一条路线。若同一批里混用两条路线，必须在 batch/result 中逐页写清 `image_generation_route`，并由主控在确认说明中解释原因。阶段3背景可以沿用阶段2路线，也可以因去字效果切换路线；但每页背景必须记录对应路线 evidence 和阶段2来源图证据。

## 尺寸和清晰度策略

阶段2和阶段3正式图片默认目标尺寸：

```text
2048x1152
```

这是 16:9 的 2K 优先目标，用于减少整页 PPT 图发糊。`1536x864` 和 1K 级别图片不是硬禁用；如果实际效果可接受，可以继续，但必须如实记录尺寸和质量风险。

统一规则：

- packet 必须写入 `target_size=2048x1152`、`preferred_minimum_size={width_px:2048,height_px:1152}`、`size_policy=preserve_generated_raster_no_downscale`。
- result 必须记录实际 `width_px`、`height_px`、`target_size`、`preferred_minimum_size`、`meets_preferred_size` 和 `size_warnings`。
- 默认 canonical 策略是保留生成器返回的原始 raster；不要为了文件体积、兼容性或旧模板主动把图片压缩、降采样或另存为更小尺寸。
- `normalize_at_stage2` 如果会缩小源图，不再作为硬错误处理，但必须记录 `postprocess_downscaled...` warning，主控据此判断是否继续。
- 如果 `codex_image_gen` 官方路线返回低于 2K 的图片，不要本地拉伸冒充 2K；应保留真实返回尺寸并记录 `meets_preferred_size=false`，主控可按实际清晰度决定继续、重试提示词、调整路线或切换 `openai_image_api`。
- 如果所有可用路线都无法稳定返回 2K，可以继续推进，但确认说明里应提醒这是低于优先目标的结果。

## Codex Image Gen 官方路线

官方路线使用内置 `image_gen` 工具，由主控大模型逐个 packet 调用。runtime 只负责派发 packet、记录 batch/result 和校验证据；本地 CLI 不会自动调用对话工具。

派发 packet：

```bash
python3 scripts/pptctl.py dispatch-cover-options --run-dir <项目目录> --route codex_image_gen
python3 scripts/pptctl.py dispatch-stage2-trial-first5 --run-dir <项目目录> --route codex_image_gen
python3 scripts/pptctl.py dispatch-stage2-remaining --run-dir <项目目录> --route codex_image_gen
python3 scripts/pptctl.py dispatch-image-generation --run-dir <项目目录> --stage stage3-background --route codex_image_gen
```

主控执行：

1. 读取 packet 中的 `prompt` 和 `image_gen_input`。
2. 阶段2使用 `image_gen` generate；阶段3使用 `image_gen` edit，并先用 `view_image` 检查本地阶段2来源图，使参考图进入对话上下文。
3. 在 prompt 中明确 16:9、2K、`2048x1152` 和高清锐利。内置工具不保证一定按尺寸参数返回，所以不要把 `image_gen_input.size` 当作已达成证据。
4. 将最终选定输出复制到 packet 的 `expected_output_relpath` 或临时项目路径，默认不主动降采样或压缩。
5. 运行 `record-image-result`，传入 `provider=codex_image_gen`、`source=codex_image_gen`、`generation_id`、`tool_call_id` 和 `image_gen_result_id`。如果未提供 `--image-gen-evidence-path`，runtime 会在 `_state/.../image_gen_calls/` 自动写 controller-recorded evidence，并读取实际图片尺寸入账。

记录示例：

```bash
python3 scripts/pptctl.py record-image-result \
  --run-dir <项目目录> \
  --packet <packet.json> \
  --image <image_gen输出图> \
  --provider codex_image_gen \
  --source codex_image_gen \
  --generation-id <generation-id> \
  --tool-call-id <tool-call-id> \
  --image-gen-result-id <image-gen-result-id>
```

正式 result 至少包含：

```json
{

  "image_generation_route": "codex_image_gen",

  "image_gen_result_id": "image-gen-result-id",
  "image_gen_evidence_path": "_state/阶段2/image_gen_calls/stage2-slide-001.json",
  "execution_group_id": "stage2-image-gen",
  "prompt_hash": "sha256:...",
```

## OpenAI Image API 中转路线

中转 API 路线继续使用 OpenAI-compatible batch runner。

默认配置：

- Grsai 控制台/文档入口：`https://k.grsai.com/`
- `base_url`：`https://grsai.dakka.com.cn/`
- 生成端点：`/v1/draw/completions`
- API key：优先从环境变量 `PPT_IMAGE_API_KEY` 读取；没有环境变量时读取本机密钥文件 `~/.codex/secrets/ppt-skill-v2/image_api_key`，也可通过 `PPT_IMAGE_API_KEY_FILE` 指定其他本机密钥文件。密钥不能写入 Skill 文档、项目产物、batch 或日志。
- 模型：`gpt-image-2-vip`
- 默认尺寸：`2048x1152`
- 默认质量：`high`
- 单次生图任务超时：`500s`，覆盖 API 请求、响应解析和返回图片 URL 下载。
- 单个 batch/run 同组最大并发：`6`；多个独立 batch 可以由主控同时运行，不设全局互斥。
- Grsai 返回的公网图片 URL 必须写入 evidence/result 的 `provider_image_url`；阶段3若基于 Grsai 阶段2图去字，packet 使用 `/v1/draw/completions` 并把该 URL 放入 `urls`。

首次使用可先配置一次本机密钥文件：

```bash
python3 scripts/pptctl.py configure-image-api-key --stdin
python3 scripts/pptctl.py image-api-key-status
```

派发和执行：

```bash
python3 scripts/pptctl.py dispatch-cover-options --run-dir <项目目录> --route openai_image_api
python3 scripts/pptctl.py dispatch-stage2-trial-first5 --run-dir <项目目录> --route openai_image_api
python3 scripts/pptctl.py dispatch-stage2-remaining --run-dir <项目目录> --route openai_image_api
python3 scripts/pptctl.py dispatch-image-generation --run-dir <项目目录> --stage stage3-background --route openai_image_api

python3 scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage cover-options
python3 scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage stage2-trial-first5
python3 scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage stage2-remaining
python3 scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage stage3-background
```

`--stage stage2` 只用于主控明确决定跳过试样时运行全套正式整页图片；新流程主路径是 `stage2-trial-first5` 通过后再运行 `stage2-remaining`。

正式 result 至少包含：

```json
{

  "source": "openai_image_api",
  "image_generation_route": "openai_image_api",
```

`tool_call_id` 和 `image_gen_result_id` 可作为兼容字段保留，但中转路线的正式判断以 `api_call_id`、`image_api_result_id` 和 `api_evidence_path` 为准。

## Batch 与并发

所有正式生图都必须有 batch manifest：

- 封面候选：`_state/阶段2/cover_options/batches/<execution_group_id>.json`
- 阶段2B试样：`_state/阶段2/trial_first5/batches/<execution_group_id>.json`
- 阶段2正式图片：
  - `codex_image_gen`：`_state/阶段2/image_gen_batches/<execution_group_id>.json`
  - `openai_image_api`：`_state/阶段2/image_api_batches/<execution_group_id>.json`
- 阶段3保真去字背景：
  - `codex_image_gen`：`_state/阶段3/image_gen_batches/<execution_group_id>.json`
  - `openai_image_api`：`_state/阶段3/image_api_batches/<execution_group_id>.json`

中转 API 路线必须并发生成：

- 阶段2A 四张封面候选必须作为同一个 `execution_group` 并发运行图片 API 批量执行器。
- 阶段2B 试样必须作为独立 `execution_group` 并发运行图片 API 批量执行器；默认3页确认范围，最多5页，可追加关键复杂页；已由选中封面候选转正的页面直接复用，不再进入试样 batch。
- 阶段2B 试样通过后的剩余图片页必须按 packet 的 `execution_group` 并发运行图片 API 批量执行器。
- 阶段3保真去字背景必须按 packet 的 `execution_group` 并发运行图片 API edits/urls 路线，并把阶段2页面图作为 reference/edit 输入。

官方 `image_gen` 路线同样必须按 packet 和 batch 入账；受对话工具能力限制，主控可以逐个调用工具，但不能跳过 batch manifest、packet、evidence 或逐张 result 记录。

## 图片用途

正式图片用途分四类：

- `cover_option`：阶段2A四张封面候选；用户选中且质量通过的候选可直接转正为封面页 `full_slide`。
- `trial_first5`：阶段2B试样图，供用户确认视觉、文字、密度和风格方向；名称沿用历史目录，默认不代表必须生成5页。
- `full_slide`：阶段2B正式整页页面图，后续打包为图片版 PDF。
- `stage2_text_removed_background`：阶段3保真去字背景图，正式结果必须有 `background_route=stage2_preserve_text_removed_background` 和 `source_stage2` 证据。
- `stage3_background`：旧阶段3无字背景图 purpose，只作为 legacy 识别，不作为新的正式 production 路线。

封面候选不能整组进入阶段2正式页面图，未选中的候选永远不能进入图片版 PDF。用户选中且主控检查通过的封面候选应直接 promotion 为正式 `full_slide` 封面结果，避免阶段2B重复生图。试样必须经用户确认和 runtime promotion 后，才能进入正式 `full_slide` results；已由封面候选转正的页面不再进入试样生图 packet。用户确认通过的试样页默认复用为正式页面，不为生成全套图片而重生。图片版 PDF 只使用 `full_slide`。

## Canonical 图片策略

请求尺寸不等于最终返回文件一定是该像素尺寸。阶段2和阶段3必须使用同一套 canonical 策略：

- `preserve_api_raster`：阶段2确认图、阶段3背景和坐标计划都保留实际生成返回尺寸。字段名沿用历史命名，也适用于 `codex_image_gen`。
- `normalize_at_stage2`：阶段2入账时就生成 canonical 可见图，阶段2 PDF、阶段3 reference、阶段3背景和坐标计划都使用 canonical 图。

禁止只在阶段3单独归一化、而阶段2用户确认图仍保留原始尺寸。若发生归一化，必须记录 `original_api_output`、`postprocess.manifest_path`、原图 sha、canonical 图 sha、尺寸和方法；证据仍指向真实原始输出，正式 `image_result.image_path` 指向用户可见 canonical 输出。归一化如果把生成原图降采样到更小尺寸，应写入 `size_warnings`，由主控判断是否接受。

## 提示词要求

- 画面中文字必须是中文。
- 不出现英文占位词、拼音、乱码、假字或 lorem ipsum。
- 每页提示词要包含页面目的、视觉层级、中文标题、关键内容和风格约束。
- 封面候选提示词要四种风格明显不同。
- 试样和正式图片提示词都要继承用户选中的 `deck_style.json` 和 `layout_intent.json`。
- 阶段3保真去字背景提示词必须明确以阶段2参考图做图像编辑，只移除可编辑文字，不重新设计构图，不重生同风格背景。

## 禁止冒充

以下不能冒充正式图片：

- 本地擦字。
- inpaint 或本地修补。
- HTML/canvas/SVG 渲染。
- 浏览器截图。
- source replay。
- fixture。
- copied source render。
- 复制旧图冒充新图。
- 只有图片文件，没有 packet、batch、对应路线 evidence 和 result 记录。

## 主控检查

主控大模型在提交用户确认前检查：

- 图片是否真实来自选定正式路线：默认 `codex_image_gen`，或显式 `openai_image_api`。
- 每张 result 是否有 `image_generation_route`、对应结果 ID、对应 evidence path、`image_sha256` 和 batch 记录。
- 中转 API 路线同组多张图片是否按并发方式调用。
- 阶段2和阶段3是否使用一致 canonical 图片策略；如有 postprocess，原始输出和 canonical 输出是否都可追溯。
- 试样是否先于剩余页面供用户确认。
- 已选封面候选是否在质量通过后直接转正，且未进入阶段2B重复生图。
- 试样 promotion 是否保留原 trial result、trial image 和 evidence。
- 中文文字是否可读。
- 页面主题是否明确。
- 风格是否统一。
- 阶段3结果是否有 `source_stage2.image_path`、`source_stage2.image_sha256` 和保真去字 route。
- 阶段2/阶段3正式图是否达到 2048x1152 优先目标；未达到时是否记录 `meets_preferred_size=false` 和 `size_warnings`。
- 是否存在任何后处理把生成图压缩、降采样或另存成更小尺寸；如存在，是否已作为质量风险记录。
- 信息层级是否清楚。
- 是否需要返工。
