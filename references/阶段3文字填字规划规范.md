# 阶段3文字坐标复刻规划规范

阶段3文字规划使用 `_state/阶段3/editable_coordinate_plan.json`，不再使用旧 `text_fill_plan 3.0` 作为正式输入。

## 一句话

```text
文字内容来自 content.json
文字归属来自 text_ownership_map
文字坐标必须精准识别自阶段2确认图几何
用户确认 editable_coordinate_plan 后，OfficeCLI builder 才按计划执行
```

## 文字归属账本

先写 `_state/阶段3/text_unit_split_plan.json`，再写 `_state/阶段3/text_ownership_map.json`。

可用 `create-text-ownership-map-draft` 从 split plan 或阶段1 content 生成 ownership 草稿；草稿只减少手写负担，不替代主控判断。主控必须复核每条文字属于 `editable_page_layer` 还是 `raster_visual_layer` 后，再用 `record-text-ownership-map` 正式入账。

`text_unit_split_plan.json` 只根据阶段1每页干净逐字稿确认可编辑文字拆分，不使用 OCR 或图片识别文字。每个 `split_unit` 至少记录：

- `split_unit_id`
- `text`
- `content_source`
- `semantic_role`
- `style_role`
- `visual_group_id`
- `must_be_separate_shape`
- `restore_as_editable`
- `background_action`

如果 split plan 存在，ownership map 必须通过 `split_unit_id` 承接所有 `restore_as_editable=true` 且 `background_action=remove_and_restore` 的 split units。

`text_ownership_map.json` 记录：

- `editable_page_layer`：标题、正文、关键数字、来源注释、页面信息标签等，需要去字后恢复为 PPT 原生文本。
- `raster_visual_layer`：设备屏幕、包装标签、插画内部标注、截图内部细节等，保留在背景。
- `unresolved_items` 必须为空，否则不能生成正式背景和坐标计划。

## 拆字颗粒度

拆字按视觉文本对象拆，不按页面或大段落粗合并：

- 封面标题、副标题、主讲人、时间必须拆成不同 `text_unit`。
- 卡片页每张卡片的标题、正文、编号、标签分别拆。
- 列表页每条 bullet 独立拆；不同缩进、不同强调色或不同图标前缀的 bullet 不合并。
- 流程页每个节点的编号、节点标题、节点说明分别拆。
- 图表页的标题、图例、注释、数据标签如要恢复为可编辑文字，分别拆；复杂图表内部文字可归入 `raster_visual_layer` 保留在背景。
- 页眉、页脚、章节标签、页码、来源注释分别拆。
- 只要位置、字号、颜色、容器、语义层级或对齐方式不同，就必须拆成不同 `text_unit`。

禁止把多个不相邻区域、多个卡片、多个 bullet、多个流程节点或整页正文合成一个 `text_unit`。拆得不确定时宁可多拆，不要粗合并。

## 坐标计划

`editable_coordinate_plan.json` 必须包含：

- `coordinate_mode=approved_image_geometry`
- `slides[].source_image`：阶段2确认图路径、宽高和 sha。
- `slides[].stage3_background_image`：阶段3无字背景路径、宽高、sha 和 `source_stage2_sha256`。
- `slides[].coordinate_canvas`：最终填字画布，basis 固定为 `stage3_background_image`，并记录从阶段2到阶段3的 scale。
- `text_units[]`：每个可编辑文字单元。
- `text_units[].ownership_id`：必须存在于 `text_ownership_map`。
- `text_units[].split_unit_id`：新链路中必须对应同页 `text_unit_split_plan` 的可编辑 split unit。
- `text_units[].style_profile_id`：建议对应 `font_calibration_profile.profiles[].style_profile_id`；缺失或未命中时记录 warning，由主控结合 probe 和真实渲染判断是否返工，不作为记录 coordinate plan 的硬门槛。
- `text_units[].visual_group_id`：用于追踪卡片、流程节点、列表组等视觉组。
- `content_source` 和 `text`：文字必须来自阶段1内容资产，不得来自 OCR。
- `display_text` 和 `wrap_policy`：多行正文、卡片正文、标签等可以使用手工换行；`display_text` 只能加入换行和必要排版空白，不得改字。
- `geometry_source`：说明坐标来自检测、人工标注、视觉辅助标注或主控修正；必须基于阶段2确认图，并写明 method 与 human_reviewed=true。
- `box_px` 和 `relative_box`：分别用于贴合阶段2图和 PPT 坐标换算。
- `font`、`paragraph`、`fit_policy`：填字前写清字体、字号、颜色、对齐、行距、内边距、溢出策略。
- `native_elements`：只记录少量需要恢复为 PPT 原生对象的底形，如 badge、编号圆点、色条和简单线条；复杂插画、照片和复杂图表仍保留在背景。

可用 `create-editable-coordinate-plan-draft` 生成坐标草稿和预览；草稿使用占位几何，仅帮助主控开始标注。`basis.status=draft` 的 coordinate plan 会被正式 `record-editable-coordinate-plan` 拒绝，必须由主控替换为阶段2确认图上的真实坐标并完成复核后再入账。

## 字体校准

复杂页先选 1 页做真实 OfficeCLI native style probe，再记录 `_state/阶段3/font_calibration_profile.json`。profile 用于理清：

- `font_size_scale`
- `line_height_scale`
- `bold`
- `text_box_insets_pt`
- `vertical_align`
- `horizontal_align`

`font_calibration_profile.render_probe.review_status` 未通过时，coordinate plan 仍可记录为试样或修正版，但 warning 必须显式标出 profile 状态、字号/行高/内边距风险。是否先补跑 probe、局部返工，还是继续交给用户看坐标复刻，由主控大模型基于复杂页真实渲染对比判断。PIL 文字效果预演只用于快速排查位置，不是字体校准证据。

## 禁止

- 不用 OCR 或图片识别文字作为内容来源。
- 不让 OfficeCLI builder 临时猜坐标或重排版式。
- 不把多个独立视觉文本对象合并成一个 `text_unit`。
- 不把一页文字、一个段落组、多个 bullet 或多个卡片文字合成一个 PPT 文本框。
- 不使用未确认的阶段2试样图作为坐标来源。
- 不使用非阶段2确认图作为 `source_image`。
- 用户未确认 `_state/阶段3/editable_coordinate_plan.json` 前，不运行 `build-editable-brief`，不运行 OfficeCLI builder 填字。
- 不从旧 PPTX、旧 QA 或旧 fixed overlay 文件继承过期坐标。
- `fit_policy.auto_shrink` 默认必须是 `false`；溢出要返工坐标或文案，不能静默缩小。
- 不允许 `source_image.path` 指向阶段2原图但尺寸写成归一化图尺寸；path、sha 和 width/height 必须对应同一个真实文件。
- 不允许阶段2保留 API 原始尺寸、阶段3单独归一化后继续混用旧坐标。

## 填字颗粒度

OfficeCLI builder 填字必须按 `editable_coordinate_plan.slides[].text_units[]` 顺序逐个执行：

1. 为当前 `text_unit_id` 创建一个同名或可追溯命名的 PPT 原生文本 shape。
2. 只填入该 `text_unit.text`，不得夹带其他 text unit 的文字。
3. 使用该 text unit 自己的 `relative_box`、字体、字号、颜色、对齐、内边距和 fit policy。
4. 写入执行报告时逐个记录 planned/actual 坐标、字号和颜色。

一个 `text_unit` 对应一个 PPT 文本对象；一个 PPT 文本对象不得承载多个 `text_unit`。

## 用户确认点

`record-editable-coordinate-plan` 只表示坐标计划已记录，不表示可以开始填字。记录后状态应等待用户确认阶段3文字坐标复刻；只有用户确认无误并写入 `approve_stage3_coordinate_plan_start_text_fill` 主控决策后，才能进入 OfficeCLI 坐标填字。

用户确认材料至少包含：

- 坐标复刻预览：阶段3无字背景 + text unit 红框。
- 文字效果预演：阶段3无字背景 + 计划字号/颜色/换行 + 少量 native_elements 底形。

文字效果预演只是填字前的轻量确认材料，不作为最终 PPT 像素级验收，也不触发 AI 自动反复调参。

## 执行报告

OfficeCLI builder 生成 PPTX 后，运行：

```bash
PYTHONPATH=scripts/runtime python3 -m ppt_skill_v2.cli build-coordinate-execution-report \
  --pptx <pptx> \
  --coordinate-plan <run_dir>/_state/阶段3/editable_coordinate_plan.json \
  --output <run_dir>/_state/阶段3/text_fill_execution_report.json
```

报告使用 `schema_version=2.0`，必须覆盖全部 `coordinate_text_units`，并记录 OfficeCLI/PPTX/OOXML 反查到的真实 relative box、字体槽、字号、颜色、行距、内边距和对齐。planned 侧应保留 `split_unit_id`、`style_profile_id`、`visual_group_id`、字重、行距和内边距，方便 QA 对回问题来源。

## QA

阶段3 QA 使用坐标复刻 QA v2：

- contact sheet 覆盖阶段2图、阶段3背景和最终 PPTX 渲染。
- 抽样页和高风险页记录 `checked_text_unit_ids`；全部文字单元覆盖由 coordinate execution report 负责。
- checks 至少覆盖：坐标单元覆盖、文字准确性、原生渲染对齐、无明显重叠/溢出、背景保真、高风险页复查。
- 高风险页必要时补 `native_render_check.json`。
- QA 新流程可选记录 `native_style_probe`，并可兼容读取旧 `font_probe`；同时可记录 `split_granularity_review`，用于说明 probe 对比和高风险页拆分复核结论；这些字段不新增用户确认点。
- QA 可选引用 `ai_quality_profile`、`controller_review_plan`、`accepted_quality_tradeoffs` 和 `recommended_high_risk_coverage`，用于说明质量画像推荐页是否已复核、哪些风险被接受为人工后调项；这些字段只帮助主控复盘，不把质量画像变成硬门禁。
